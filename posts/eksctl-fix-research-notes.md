# Research notes: fixing eksctl's missing NVIDIA device plugin node restriction

Read-only research against the local fork at `/Users/jagsharm/code/forks/eksctl`, done before writing any
code, to de-risk the planned `SetNodeSelector` PR. Nothing here is implementation — see "Open questions"
at the end for what's still genuinely undecided.

## 1. The embedded manifest

`pkg/addons/assets/nvidia-device-plugin.yaml` — the base DaemonSet template. Full relevant spec section:

```yaml
spec:
  template:
    spec:
      tolerations:
      - key: nvidia.com/gpu
        operator: Exists
        effect: NoSchedule
      priorityClassName: "system-node-critical"
      containers:
      - image: nvcr.io/nvidia/k8s-device-plugin:v0.20.0
        ...
```

**No `affinity`, `nodeAffinity`, or `nodeSelector` anywhere in this file.** Only the toleration. This
confirms a new `SetNodeSelector` method (or an equivalent static YAML edit) doesn't need to merge with
anything pre-existing — it's additive from a clean slate.

## 2. Real signatures/definitions

**`api.HasInstanceType` / `api.HasInstanceTypeManaged`** — `pkg/apis/eksctl.io/v1alpha5/nodegroups.go:6` and `:21`:

```go
// HasInstanceType returns whether some node in the group fulfils the type check
func HasInstanceType(nodeGroup *NodeGroup, hasType func(string) bool) bool {
	if hasType(nodeGroup.InstanceType) {
		return true
	}
	if nodeGroup.InstancesDistribution != nil {
		for _, instanceType := range nodeGroup.InstancesDistribution.InstanceTypes {
			if hasType(instanceType) {
				return true
			}
		}
	}
	return false
}

// HasInstanceTypeManaged returns whether some node in the managed group fulfils the type check
func HasInstanceTypeManaged(nodeGroup *ManagedNodeGroup, hasType func(string) bool) bool {
	if hasType(nodeGroup.InstanceType) {
		return true
	}
	for _, instanceType := range nodeGroup.InstanceTypes {
		if hasType(instanceType) {
			return true
		}
	}
	return false
}
```

**Important:** a node group is not guaranteed to have exactly one instance type. `NodeGroup` can have
multiple via `InstancesDistribution.InstanceTypes` (spot/mixed-instance policy); `ManagedNodeGroup` can have
multiple via its own `InstanceTypes` field directly. Any fix that collects "the instance type of this node
group" needs to collect a **set**, not assume a single string per group.

**`instance.IsNvidiaInstanceType`** — `pkg/utils/instance/instance.go:25`:

```go
// IsNvidiaInstanceType returns true if the instance type has NVIDIA accelerated hardware
func IsNvidiaInstanceType(instanceType string) bool {
	return InstanceTypesMap[instanceType].NvidiaGPUSupported
}
```

Backed by `InstanceTypesMap` (`pkg/utils/instance/instance_types.go`) — **13,611 lines**, header comment
`// / Generated by \`ec2geninfo\``. This is an auto-generated, comprehensive table of every EC2 instance
type with metadata (`NvidiaGPUSupported`, `NeuronSupported`, `EFASupported`, etc.), not a hand-maintained
list. See section 5 below — this matters a lot for which implementation approach is actually better.


Key pattern: `addons.NewNvidiaDevicePlugin(nil, "us-west-2", false, config).(*addons.NvidiaDevicePlugin)` —
constructs the real plugin via its exported constructor (passing `nil` for the raw k8s client, since
`SetTolerations` never touches it), casts to the concrete type to call the method directly, then asserts on
the mutated `spec`. A `SetNodeSelector` test suite would follow this exact shape — same `BeforeEach`, same
node-group construction style, asserting on `spec.Spec.Affinity` instead of `spec.Spec.Tolerations`.

## 4. `applyDevicePlugin` / `SetTolerations` call chain

`pkg/eks/tasks.go`:

```go

func (n *devicePluginTask) Do(errCh chan error) error {
	// ...
	devicePlugin := n.mkPlugin(rawClient, n.clusterProvider.AWSProvider.Region(), false, n.spec)
	if err := devicePlugin.Deploy(); err != nil {
		// ...
	}

func newNvidiaDevicePluginTask(/* ... */) *devicePluginTask {
	t := devicePluginTask{
		// ...
		mkPlugin: addons.NewNvidiaDevicePlugin,
	}
	// ...
}
```

Note: `planMode` is **hardcoded to `false`** at this real call site (`n.mkPlugin(rawClient, region, false, n.spec)`)
— plan-mode isn't actually threaded through here in practice, so a new `SetNodeSelector` method doesn't need
special plan-mode handling beyond what `SetTolerations` already does (i.e., none).

The task itself is gated by the `--install-nvidia-plugin` flag (default `true`), wired through
`pkg/ctl/cmdutils/nodegroup_flags.go:74` and consumed in `pkg/eks/tasks.go:369`
(`tasks.Append(newNvidiaDevicePluginTask(c, cfg))`) — this is a single all-or-nothing decision ("run this
task at all"), separate from the per-node-group filtering that happens *inside* `SetTolerations` itself.
A `SetNodeSelector` method would be invoked the same unconditional way, doing its own internal per-node-group
filtering exactly like `SetTolerations` does now.

## 5. Existing NodeAffinity/Affinity patterns — and a finding that changes the approach

Two places already use `NodeAffinity` in this codebase, and they represent **two different, inconsistent
patterns** for restricting a device-plugin DaemonSet to specific hardware:

**Pattern A — dynamic Go, node-group-driven (what `SetTolerations` does today, Nvidia only).**
Computes something from the user's actual configured node groups at cluster-creation time.

**Pattern B — static, hardcoded YAML list (what EFA and Neuron do, not Nvidia).**
`pkg/addons/assets/efa-device-plugin.yaml`:

```yaml
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
              - matchExpressions:
                - key: "node.kubernetes.io/instance-type"
                  operator: In
                  values:
                    - m5dn.24xlarge
                    - m5dn.metal
                    - m5n.24xlarge
                    # ... ~20 more hardcoded EFA-capable instance types
```

`pkg/addons/assets/neuron-device-plugin.yaml` — identical shape, hardcoded `inf1.*`/`inf2.*` values.

**This is the important finding.** EFA and Neuron ship a static, hand-maintained list of every instance type
that supports that hardware, baked directly into the embedded YAML — no Go logic computes it, it's just
data. If Nvidia followed the *same* pattern, the "fix" would be a one-line-per-instance-type YAML edit to
`nvidia-device-plugin.yaml`, not a new Go method at all.

But this is very unlikely to be the right call for Nvidia specifically, because of what section 2 found:
`IsNvidiaInstanceType` is backed by a 13,611-line **auto-generated** table (`ec2geninfo`), covering every
NVIDIA GPU instance type AWS has ever shipped, kept current by tooling. EFA-capable and Neuron-capable
instance types are a much smaller, slower-growing set (~20-30 entries each) — plausibly small enough that
hand-maintaining a static YAML list is acceptable for them, but not for the much larger and faster-growing
Nvidia GPU family (p2/p3/p4/p5, g3/g4/g5/g6, and future families). That's plausibly *why* Nvidia already has
dynamic `SetTolerations` logic while EFA/Neuron don't need one — and it argues for `SetNodeSelector` doing
the same: computed dynamically in Go from the already-comprehensive, already-generated `IsNvidiaInstanceType`
check, not a new hand-maintained YAML list that would need separate upkeep.

Net effect on the plan: **the dynamic Go approach (mirroring `SetTolerations`) is still the better-justified
choice**, but this is a real design fork a maintainer could reasonably disagree on, and it's worth explicitly
asking about in the issue/PR rather than assuming.

## 6. CONTRIBUTING.md requirements

Key points from `CONTRIBUTING.md`:

- **DCO, not CLA** — no special sign-off action required beyond agreeing to the Developer Certificate of
  Origin (see the `DCO` file); no action needed unless asked.
- **Fork + branch from `main`**: `git checkout -b <feature-name>`.
- **"Align with existing patterns and standards"** — explicitly called out, which is exactly why matching
  `SetTolerations`'s shape (rather than inventing a new style) is the right instinct.
- **Commit in small chunks**, proper commit message format: short imperative subject line (≤70 chars), blank
  line, body explaining *why*, wrapped at 80 chars.
- **Tests required** — "Be sure to include at least unit tests to cover your changes." Points to
  `pkg/actions/addon` as a model example. Also: they're moving away from `mockery` toward `counterfeiter`
  for fakes where mocking is needed (likely not needed here — `SetTolerations`'s own tests don't mock
  anything, they construct real `api.ClusterConfig` values directly).
- **Build/test locally**: `make install-build-deps && make build`, `make test` to run unit tests.
- **Autogenerated files**: editing `pkg/apis/eksctl.io/v1alpha5/types.go` requires regenerating derived
  files via `make test` before committing — likely **not** relevant here unless the fix requires adding a
  new field to `NodeGroup`/`ManagedNodeGroup` (it shouldn't; existing fields already carry everything
  needed).
- **PR guidelines**: thorough description (don't just link the issue — explain *how* you solved it, not just
  the problem), snappy imperative title (goes into release notes), manual testing evidence encouraged
  (snippets/screenshots), new tests for new code, squash commits before submitting, allow maintainer edits.
- **Draft PRs** are fine/expected if still in progress.
- Response time: bug reports ~a couple of working days; wait at least 7 days before nudging.

## Open questions / things to double-check when actually writing the fix

1. **Dynamic vs. static list (section 5)** — genuinely worth asking the maintainers directly in the
   issue/PR discussion rather than deciding unilaterally, given EFA/Neuron set a different precedent than
   what we're proposing for Nvidia. Our reasoning (list size/growth rate) is sound but is an assumption, not
   something confirmed by a maintainer.
2. **Exact `corev1.Affinity` construction** — haven't yet located a Go-code example in this repo of *building*
   a `NodeAffinity` from scratch (only found `addArm64NodeSelector` in `pkg/addons/default/kube_proxy.go`,
   which *mutates an already-existing* affinity block and errors out if one isn't present — not directly
   reusable, since our manifest has no pre-existing affinity to mutate). Need to write this from scratch
   using `corev1.NodeSelectorRequirement`/`MatchExpressions` with `operator: In`, following the same shape
   the EFA/Neuron YAML already uses, just constructed in Go instead of hardcoded.
3. **Label key constant** — should confirm whether to use the raw string `"node.kubernetes.io/instance-type"`
   (as the EFA/Neuron YAML literally does) or a `corev1` well-known label constant if one exists for it,
   for consistency with whatever style eksctl/k8s client-go conventions prefer.
4. **`EFADevicePlugin.SetTolerations` body** — not yet read directly (only confirmed `NeuronDevicePlugin`'s is
   a no-op `return nil`); worth a quick check before assuming EFA's is also a no-op, though it's very likely
   given EFA's restriction already comes entirely from its static YAML affinity.
5. **Test file location for a new method** — presumably added to the same `pkg/addons/device_plugin_test.go`
   under a new `Describe("SetNodeSelector", ...)` block, mirroring `SetTolerations`'s — should confirm no
   separate test file convention is expected instead.
6. **Scope of the PR** — whether to touch only `NvidiaDevicePlugin`, or also add (no-op or otherwise)
   `SetNodeSelector` stubs to `NeuronDevicePlugin`/`EFADevicePlugin` for interface consistency, given
   `DevicePlugin` is a shared interface all three implement. Adding a new interface method means *all*
   implementers need it, even if two of them are no-ops — worth confirming this is the expected/acceptable
   shape rather than, e.g., a separate optional interface.
